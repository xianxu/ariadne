🤖:[ToolOpus*]

Let me make sure I understand the shape of what you've built before reacting, since a few things are ambiguous and I don't want to give generic advice.

Here's my read of your pattern:

- **Phase 1 (lock):** issue → `working`, push to origin as a distributed lock.
- **Phase 2 (design):** work directly on main, one file per issue in `workshop/`, commit straight to main. Low conflict risk because each issue owns its own file.
- **Phase 3 (implement):** `sdlc change-code` gates the transition to actual code changes, often creating a branch.

The core insight I think you've landed on: **separate the artifacts by conflict profile, and pick the concurrency strategy per artifact.** Design docs are append-mostly, per-issue, low-conflict → main is fine. Code is shared-surface, high-conflict → branch. That's genuinely sound, and it's a more thoughtful decomposition than the usual "everything goes on a branch" dogma.

A few critical observations and questions:

### What works well
- **Per-issue file in `workshop/` is the key trick.** It turns design into an embarrassingly parallel problem. As long as one issue ≈ one file, you essentially never conflict. This is the same reason tools like changesets (one file per change) avoid the changelog merge-conflict hell.
- **Issue-state-as-lock is pragmatic** for a solo founder. It's advisory, not enforced, but you don't need enforcement when N=1.

### Where I'd push back / probe
1. **The lock is [a distributed mutable flag with no expiry].** For you alone this is fine. But you framed this as "someone would be able to design in parallel" — the moment N>1, a `working` flag with no owner field and no lease/timeout is a stale-lock generator. Worth asking now: does the lock record *who* and *when*, even if you don't enforce it yet?

2. **"Often we do" create a branch is the part [that smells].** A gate whose behavior is "depends on the situation" is a gate that will eventually be applied inconsistently. What's the actual decision rule? If you can't state it as a rule, future-you (or a second person) can't follow it. My instinct: make the *default* deterministic (always branch) and require an explicit flag to opt out (`--on-main`), rather than the reverse.

3. **Design on main, code on branch creates a split-brain window.** If design commits land on main while implementation lives on a branch, the branch can drift from the design that's still evolving on main. Concretely: [does Phase 3 freeze the `workshop/` file], or can design keep mutating on main while code is in-flight on the branch? If the latter, which is the source of truth when they disagree?

4. **[What does "done" do to the lock]?** You described acquisition but not release. Issue → `working` locks it; what transitions it back, and does that happen on merge, on close, or manually? Stale `working` states are the failure mode here.

### The question behind the question
I think you're really asking *"is this a sound foundation that scales from 1 to a small team without rework?"* — because you mention parallel designers and individually-driven implementation despite being solo today. If that's the intent, my honest take: **the design/code split is sound and will scale; the lock and the "often we branch" gate are the two things that won't survive contact with a second person** unless you tighten them now.

Is your priority right now (a) minimal friction for solo work, or (b) building the gates correctly so the 1→team transition is painless? [Those pull in different directions on points 1 and 2, and I'd answer differently depending on which you care about.]

Good — your answers resolve most of my concerns, and a couple of them are better-reasoned than my original objection. Let me respond point by point, then tackle the "I want both" tension directly because that's the real meat.

### On the lock: I concede, mostly
You're right. **The git commit *is* the owner+timestamp record**, so you don't need to put `who`/`when` in the flag — it's already in the DAG. That's actually more elegant than what I proposed: a denormalized owner field could go stale or lie, but the commit that flipped the issue to `working` is ground truth. So "build a tool to attribute and steal the lock" is the correct move, and it's recoverable rather than enforced.

The one residual: stealing a lock is a *social* operation (you're preempting someone). The tool can attribute it trivially; what it can't do is tell you *whether it's safe* to steal. But that's a team-norms problem, not N=1, so park it.

### On worktree vs in-place branch: your framing is sharper than mine
You've reframed the gate correctly. The decision isn't "branch or not" — **it's always branch; the only variable is the branch's *physical realization*** (in-place checkout vs worktree). That's a much cleaner axis. And your rule-of-thumb is real:

- **Dev-tooling repos** (like ariadne itself): worktree is *leaky* because tools assume paths, configs, hardcoded roots, etc. So in-place is the sane default.
- **Web apps / clean repos**: worktree is near-free, so it becomes the default.

So the "situational" part isn't ad-hoc after all — it correlates with **repo type / path-sensitivity**. That's a statable rule, which was my actual complaint. I'd just suggest making it a *per-repo config default* (`sdlc.worktree = false` for ariadne) rather than a per-invocation human judgment, so the judgment is made once, not every time.

### On freezing workshop/ on the branch: agreed, and the rationale is the important part
Freeze-on-branch is the right call, and your reasoning is the load-bearing part: **once implementation starts, the design becomes an internal detail-in-progress that the outside world shouldn't observe until done.** That's an information-hiding / encapsulation boundary applied to *process*, not just code. I like it.

One sharp edge worth naming: if design and code are frozen together on the branch, then **discovering-during-implementation-that-the-design-was-wrong** is handled *inside* the branch (you edit the frozen workshop file there, and it re-merges to main on done). 🤖<That's correct — just make sure the merge of the workshop file back to main is *expected*>[the convention I'm thinking about is once an issue is claimed, only one guy is working on it, intially still on main, but once real, more conflicting work starts, it branches out], not treated as a surprise conflict. The frozen file is a fork that rejoins, not a read-only snapshot.

### "I want both" — this is the actual design problem
Both is achievable here, but only because of a specific property of your setup, so let me state *why* it's not a contradiction rather than just cheering you on.

The friction-vs-correctness tension is usually real because **enforcement adds friction**. The escape hatch is: **make the correct path the low-friction path, and make gates advisory + recoverable rather than blocking.** Your design already does this in two places, which is why "both" is on the table:

| Concern | Solo (friction) | Team (correctness) | Why both work together |
|---|---|---|---|
| Lock | flip flag, push | steal via tooling using git attribution | Lock is *advisory + recoverable*, never blocks you solo |
| Branch realization | per-repo default | same default | Decision made once in config, zero per-task cost |
| Design parallelism | one file, commit to main | one file per issue = no conflicts | Conflict-free by data layout, not by coordination |

The principle that makes "both" coherent: **you're getting correctness from *structure* (per-issue files, git-as-ledger, freeze boundary), not from *enforcement*.** Structural correctness has near-zero friction because it doesn't gate you — it just makes the conflict-prone thing impossible by construction. Enforcement-based correctness (locks that block, mandatory reviews, CI gates) is what trades against friction, and you've mostly avoided needing it.

So my revised opinion: **the pattern is sound and genuinely does scale 1→small-team without rework**, *provided* you keep gates in the "advisory + recoverable" quadrant and resist the temptation to make them blocking as the team grows. The day you add a *blocking* gate (e.g. "can't change to `working` if someone else holds it") is the day you reintroduce the tradeoff you're currently dodging.

One probe back at you: the **release/history step** (`workshop/history`) is the one place I'd still scrutinize. When an issue's design file moves to `history`, does that move happen on the branch (and merge to main on done) or directly on main? If on the branch, two issues finishing near-simultaneously could both touch `workshop/history` — is that a directory-of-files (conflict-free) or an append-to-shared-file (conflict-prone)? That's the one spot where your otherwise-clean "one file per issue" property could leak.
