# dev-aliases: a binary whose owner needs a generated input fails to build in a fresh checkout

## Problem

`construct/dev-aliases.sh` (ariadne#57; per-slot owners since #95 M5) emits, for
each owned `cmd/X`:

    X() { ( cd OWNER && mkdir -p bin && rm -f bin/X && go build -o bin/X ./cmd/X ) || return; OWNER/bin/X "$@"; }

That assumes `go build ./cmd/X` succeeds on a clean checkout. pair's `couch` does
not: it embeds `cmd/internal/runtimebundle/assets/runtime/files`, which is
gitignored and generated by `make runtimebundle-generate` (pair `Makefile.local`).
The repo's normal `make build` runs that step first.

Observed on 2026-10-06 during pair#362's live exercises. In two fresh Couch slots
(`pair:5`, `pair:6`), every `couch` call failed before printing anything:

    cmd/internal/runtimebundle/embed.go:8:41: pattern assets/runtime/files: no matching files found

The slot's agent therefore could not reply through Couch. It worked around this by
calling `~/workspace/pair/bin/couch` directly. Older slots work only because
`make build` once ran there. Every new slot of an owner with generated build
inputs is broken the same way, which matters more now that slots are created
routinely (pair#387 reconciles them; pair#362/pair#396 schedule work onto them).

## Spec

Captured for operator review; no implementation is authorized by this issue
creation.

- **The owner declares how to prepare a dev build, and dev-aliases runs it.** The
  default stays `go build`, for owners that declare nothing. Candidate shapes:
  - a conventional owner Makefile target (e.g. `dev-prepare`) that the emitted
    function runs (`make -s dev-prepare`) before `go build` when the owner defines
    it. The owner's make prerequisites keep it cheap when up to date, and keep
    generated inputs fresh when their sources change;
  - or a per-binary declaration in the owner's `construct/` naming the build
    command.
  The choice is open. The rule is the same either way: declared by the owner, not
  guessed by dev-aliases.
- **pair adopts it.** Its preparation step generates the runtime bundle
  (`runtimebundle-generate`), so a fresh pair slot's `couch` builds. That change
  is pair's half, in pair's own tree.
- **Keep the function's contract.** It builds into the owner's `bin/`, runs from the
  caller's cwd, and stays Bash 3.2-safe. A failed preparation step fails the call
  loudly, as a failed `go build` does today.
- **Not in scope:** making pair's generated inputs unnecessary for a plain
  `go build`. That is a pair design question (the bundle is generated on purpose),
  not dev-aliases'.

## Done when

- dev-aliases runs an owner-declared preparation step before building, with a
  test in `construct/scripts/test/dev-aliases.test.sh`: an owner that declares one
  gets it in the emitted function, and one that does not keeps today's exact form.
- pair declares its step. In a freshly created pair slot, the dev-alias `couch
  --help` succeeds with no manual `make`, verified live.
