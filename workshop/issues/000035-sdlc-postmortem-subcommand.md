# sdlc postmortem subcommand — structured per-issue retrospective

## Problem

Stage 7 (Postmortem) in the SDLC arc currently has two surfaces, both narrow:

1. **`xx-introspect`** — mines accumulated transcripts across all recent sessions for cross-cutting agent-behavior patterns; weekly/biweekly cadence; produces auto-loading taste skills. Operates on the agent-evolution axis, not per-issue reflection.
2. **`workshop/lessons.md`** — single global file of rules-to-prevent-recurrence. Operator-curated, ad-hoc.

Neither answers the per-issue postmortem question: *for this specific issue we just shipped, what's the structured retrospective?* Timeline, scope shifts, velocity, surprises, learnings, crystallization candidates — none of these are systematically gathered or surfaced.

Today this happens in operator's head (or doesn't). High-quality issues get rich Log entries; lower-attention issues just ship and move on. Patterns worth crystallizing into targets get noticed only when the operator happens to remember them across sessions. Lessons worth recording in `lessons.md` get missed.

The discipline gap: every issue close should produce evidence — what worked, what didn't, what we learned, what might become a durable commitment.

## Spec

### Design — `sdlc postmortem`

New subcommand that generates a structured retrospective at issue close. Auto-dispatched from `sdlc close` (matching the milestone-close → judge auto-dispatch pattern). Writes to the issue file's new `## Postmortem` section. Form/essence split:

- **Deterministic (always run):** timeline, scope shifts, velocity. Mechanical extraction from existing ledgers — commits with `Review-Verdict:` trailers (ariadne#31), `## Revisions` entries, `actual_hours` frontmatter, project file detail blocks (when present).
- **LLM (operator-gated):** surprises, learnings, crystallization candidates. Each section is a separate LLM step; operator can approve, skip, or modify candidates before write-back. The output of the LLM steps is markdown checklist of candidates with `[accept]` / `[skip]` semantics; accepted lessons go to `workshop/lessons.md`; accepted target candidates draft a target file via `xx-datatype target` flow.

### Postmortem artifact location

Issue file's new `## Postmortem` section. Same lifecycle as the issue — moves to `workshop/history/` when archived. No parallel directory.

Output skeleton:

```markdown
## Postmortem

<!-- Generated by `sdlc postmortem --issue N` at YYYY-MM-DD. Sections marked
     [skipped] were bypassed; deterministic half is always present. -->

### Timeline (deterministic)
[per-milestone rows: date, milestone, verdict, commit]

### Scope shifts (deterministic)
[plan revisions + reasons, scope events from project file if any]

### Velocity (deterministic)
[estimated vs actual hours; per-milestone breakdown; variance commentary]

### Surprises (LLM, operator-gated)
[what changed during execution that wasn't in the plan]

### Learnings (LLM, operator-gated)
[lesson candidates with accept/skip; accepted → workshop/lessons.md]

### Crystallization candidates (LLM, operator-gated)
[target candidates with accept/skip; accepted → draft via xx-datatype target]
```

### Flags

- `--issue N` (required) — ariadne issue ID
- `--data-only` — skip all LLM sections; commit deterministic data only
- `--skip-surprises` / `--skip-learnings` / `--skip-crystallization` — per-section skips
- `--agent <name>` — agent CLI for LLM dispatch (claude | codex | gemini)
- `--no-write` — print to stdout, do not modify issue file (preview mode)

### Auto-trigger from `sdlc close`

After close mutations + verdict-tracking guard, dispatch postmortem unless `--no-postmortem` is set. If postmortem fails (LLM unavailable, etc.), close still succeeds with a warning. Same posture as milestone-close ↔ judge.

### Output flow

1. Deterministic gather: timeline, scope shifts, velocity → assembled into draft.
2. For each LLM section (unless skipped):
   a. Dispatch fresh-context subagent with section-specific prompt.
   b. Parse candidates from output.
   c. Present to operator interactively — each candidate has accept/skip.
   d. Accepted candidates feed downstream writes (lessons.md, target file drafts).
3. Write `## Postmortem` section to issue file.
4. Emit a trailer block for the operator/agent to include in their commit:
   ```
   Postmortem: complete
   Lessons-Added: <count>
   Targets-Drafted: <slug>, <slug>
   ```
   (Or `Postmortem: data-only` / `Postmortem: skipped`.)

### Out of scope (future work)

- **Auto-detection of postmortem missing** — full-issue close currently doesn't verify postmortem ran. Could add a guard analogous to the verdict guard, refusing close without postmortem evidence. Defer until we see the postmortem in practice — might be over-discipline.
- **Cross-issue learning aggregation** — once postmortems exist across many issues, a `sdlc lessons-roundup` could surface patterns across them. Defer.
- **Project-file integration** — postmortem could update project file's portfolio commentary (actual vs estimated rolled up across multiple issues). Defer.
