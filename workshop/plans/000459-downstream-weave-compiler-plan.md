# Downstream compiler compatibility implementation plan

> **For agentic workers:** Consult AGENTS.md Section 3 (Subagent Strategy) to determine the execution approach. No implementation, network publication, release, or downstream workflow edit is authorized by this draft.

**Goal:** Make downstream merge-checks reproducible with a compiler that includes #422, and reject incompatible substrate changes in Ariadne CI before they land.

**Architecture:** Recommend building the CI gateway from an explicit full Ariadne commit. Keep the selected downstream compiler separate from Ariadne's candidate compiler, and test that pinned executable against candidate vocabulary/schema inputs in disposable cold consumers. This repairs CI; ordinary startup distribution remains a separate release concern.

**Tech stack:** Existing weave CLI, Go/module checksums, Git commit identities, GitHub Actions, Python/Bash process fixtures, Homebrew/CUE already used by the pipeline.

## Diagnosis and scope

`bootstrap.sh` accepts any PATH weave whose `dependencies --help` succeeds; otherwise it installs the current tap formula. It does not pin a release or enforce #422 capability. Ariadne's `.github/workflows/merge-check.yml` builds its candidate CLI, so its own green check does not exercise the older downstream compiler.

#422 added `ship` rows and committed `.weave-sha256` ownership proof. A cold consumer has committed generated bytes and sidecars but no runtime inventory. When vocabulary changes, 0.1.0 cannot use that proof and rejects replacement. The modern ownership rule is already implemented; this item fixes distribution and the missing cross-version check, rather than weakening the ownership guard.

The workflow is a `seed` in `construct/base.manifest`: compile refreshes differing existing workflow bytes. That does not rewrite the workflow already selected for a running GitHub job or commit the result on a consumer branch; reviewed, committed workflow migrations are still required. Primary checkout reads found the shared bootstrap-based workflow in 20 downstream repositories (including indirect nous/metis descendants); actual remote workflow/branch identities must be audited before claiming fleet rollout complete. Local checkout contents alone are not deployment evidence.

## Selected design

### CI gateway acquisition

1. Read and validate the selected SHA before bootstrap. Check out `xianxu/ariadne` at that exact SHA into runner-private temporary storage; verify `git rev-parse HEAD` equals it. Use a fixed repository URL, read-only permissions, and argv/env inputs rather than interpolated PR text.
2. Select the Go toolchain from the pinned checkout's `go.mod`, with `GOTOOLCHAIN=local` for the build and no opportunistic toolchain upgrade. Module identities/checksums come from that checkout's `go.mod`/`go.sum`. A missing dependency or failed fetch is a visible CI failure, never a fallback compiler.
3. Run `CGO_ENABLED=0 go build -trimpath -o RUNNER_PRIVATE/weave ./cmd/weave` with cwd at that pinned checkout. Record source SHA, Go version and `go version -m`; require the VCS revision to equal the pin and `vcs.modified=false` when building a Git checkout. Do not claim `--version=dev` alone proves identity.
4. Put only that output directory first on downstream PATH before `./bootstrap.sh`. Keep existing dependency compilation/setup/check order. Test a misleading preinstalled 0.1.0 and prove it is not selected.
5. Ariadne's source CI continues using its candidate compiler for candidate compilation. It separately builds each supported downstream pin for conformance; it must never substitute candidate/PATH weave for the pinned executable.

### Upstream compatibility guard

Run the conformance step on **every Ariadne PR and main push**, alongside existing merge-checks, without an incomplete vocabulary-only path filter. Candidate compiler/generator changes, manifest changes and schema changes can all affect consumers. Run inside the existing merge-check job so it cannot be forgotten as an optional unrequired status. Add the pin files and new CI helper path to the local-gates matcher and its cases.

For each supported pin, create fresh isolated source/consumer trees, with no dependency fetches, builds, package installs or writes in live sibling checkouts:

- Copy the candidate top-level vocabulary sources, actual vocabulary skill directory/marker, and vocabulary-relevant candidate manifest declarations into a minimal owner layer. Derive the declaration selection from the candidate manifest, fail if the expected vocabulary producer disappears or becomes unrecognized, and retain the real declaration text rather than synthesizing a substitute producer that could hide incompatibility. Build/use the **candidate** vocabulary generator and its real CUE toolchain. Generate the complete corpus from actual candidate inputs; do not replace it with a fixed canned JSON body. Use minimal local Make/tool wiring to avoid unrelated owner tool builds, and no Brewfile or real data mounts in the fixture.
- Enumerate generated vocabulary JSON files to construct the leaf's `ship` rows; include the actual `issue.json` that motivated #459. Export every actual candidate top-level noun through the existing resolver; it deliberately excludes construct/vocabulary/testdata. Generated noun JSON is the shipped corpus. Existing positive/negative instance fixtures remain separate validation inputs (some intentionally invalid), never generated outputs or ship rows. Run those existing validation checks separately; malformed candidate CUE or generator output fails before invoking the older compiler. This guard covers exported vocabulary schemas, their producer declarations, and ownership compatibility; it does not claim compatibility of arbitrary unrelated schema files or every manifest backend.
- Seed a tracked baseline output/sidecar pair from the base revision's exported corpus (or a valid older fixture for newly introduced nouns). Confirm there is **no ownership inventory**. Point the fixture at candidate sources, then invoke the external pinned compiler's real `compile`. Require successful regeneration of the candidate corpus, correct digest sidecars and no authored data displacement. Compare expected candidate outputs, not merely exit zero: old compilers may silently ignore new manifest verbs.
- Repeat from a second cold clone containing the candidate output/sidecar pair; require a no-drift compile. A warm inventory must not be the only test, because it hides this incident.
- Negative controls: a tampered output with a stale sidecar must be refused with its bytes unchanged; missing/malformed/symlinked sidecars must not gain ownership. An ordinary undeclared authored file must never be silently overwritten. Reuse the existing ownership behavior, not an exception in the harness.
- An always-changed ownership control is required even on PRs whose base/candidate exports are identical: use one valid older committed generated output whose bytes are asserted different from the generator result, with its matching sidecar and no inventory. Run real 0.1.0 through **compile**, using a test-only admissible pin configuration so pin-membership rejection cannot masquerade as the regression. Require its authored-replacement refusal and unchanged bytes, then run the identical fixture successfully with the post-#422 executable.
+- Harness tests prove the job fails when the pinned compiler fails, changes the wrong bytes or omits a sidecar; malformed pins fail before checkout/build; candidate compiler substitution is rejected. Restore the 0.1.0 pin locally and observe a nonzero compatibility result; restore the approved post-#422 pin and observe success. No network-dependent full-compiler download/build is hidden inside default unit tests.

The real conformance script is invoked explicitly by CI after its binaries/tools are prepared; `scripts/test/weave-compatibility.test.sh` tests orchestration without network. This keeps the existing default `scripts/test/*.test.sh` runner inexpensive. CI prints the exact pin, failing phase and retained/logged diagnostic paths; empty/missing output is a failure, never a skip.

### Fleet rollout and pin maintenance

TL inventories each remote consumer workflow/pin from its actual default branch, including indirect substrate consumers and repositories without Go modules. A conditional string such as `weave-candidate` in a shared workflow does not mean the consumer builds the candidate: its module guard selects the published-formula path.

The source workflow seed gains pinned gateway acquisition and may refresh workflow bytes during compilation. The selected pin itself remains consumer-authored, not generated/seeded; new-repository setup must create it explicitly from an approved supported SHA. TL files/dispatches existing consumer migrations; their owners create ordinary per-repository issue branches from main. Each patch changes only the exact pin, gateway acquisition and required toolchain/setup tests. The proposed pin is already on main, so peer changes depend on no unlanded #459 implementation.

Operator verifies and labels every affected local-gates PR; agents never self-label. Downstream smoke: a cold checkout containing an older valid committed vocabulary/sidecar regenerates after a vocabulary change without an authored-replacement refusal. Verify exact checkout/build identity in actual CI logs. Keep #459 open until rollout evidence covers every inventoried active consumer and Ariadne's guard is landed.

For later pin changes, add the new pin to the supported set **before** migrating consumers; test both. Remove the old pin only after TL records remote evidence that no inventoried consumer still selects it. Do not claim this manual inventory is a permanent automatic proof: the source CI guarantees its declared supported set, and TL owns deployed-pin reconciliation. A consumer choosing an undeclared older pin is unsupported configuration drift. Initial retirement of already-broken 0.1.0 is an explicit operator-approved migration, not a green compatibility claim about 0.1.0.

## States, actions and recovery

Actions: edit proposal, approve exact pin, rerun same revision, inspect remote identity, migrate consumer, restore prior supported pin, publish approved release.

| Internal state / failure mode | Visible state | Recovery action | Possible loss |
|---|---|---|---|
| Local draft only | Awaiting plan approval; no rollout | Edit proposal / approve exact pin | No production state changed |
| Pin cannot be fetched or built | CI compiler acquisition failed | Rerun same revision after diagnosing availability | One runner's temporary work |
| Pinned compiler rejects candidate input | Compatibility failed with pin/path | Edit candidate or approve a compiler migration | No authored consumer data may be lost |
| Some consumers still use old pin | Rollout incomplete | Migrate consumer; retain supported old pin where it actually works | Existing old CI may remain red until migrated |
| CI run cancelled or runner dies | Check incomplete, never passed | Rerun same revision | Temporary diagnostics if not uploaded |
| Release publish reply lost (A only) | Publication unconfirmed | Inspect exact remote tag/run/release/tap identity | Partial remote publication; no automatic rollback |

There is no new long-lived service or concurrent writer: GitHub owns each job/checkout lifetime, and private fixture directories are removed on normal exit and collected with the runner otherwise (ARCH-FUNERAL). Build and compiler children are foreground, timeout/cancellation bounded by the existing job/process seam, and fully joined before cleanup. B publishes no release state machine. Do not invent a lease to coordinate independent consumer repositories: a local lock cannot make a multi-repository rollout atomic. Explicit supported pins and reviewed rollout evidence define the guarantee (ARCH-ORDER/SECURE).

This is a CI path, not an interactive hot path. Work is one compiler build per supported pin (K <= 2), then a fixed number of cold fixture compiles per pin. Corpus comparison is O(total generated bytes + file count); no per-noun rebuild or per-file whole-corpus rescan. Test doubled fixture corpora by counted file visits, not timing, if the harness introduces an explicit traversal.

that admits and executes real 0.1.0, so neither unchanged vocabulary nor a pin
membership refusal can turn the regression into a false pass. This is still a
local unapproved draft; no implementation or publication was performed.
